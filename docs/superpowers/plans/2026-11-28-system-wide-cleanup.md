# BlackSwan system-wide cleanup implementation plan
> Planning only; no implementation or live campaign authorised by this document. Implement in independent commits with superpowers:executing-plans or subagent-driven-development, test-first and verification-before-completion.

**Goal:** Remove self-imposed delays, duplicated data paths and unnecessary live-mode branches without changing the detector baseline, selection mathematics, executable-price meaning, campaign exposure or receipt-based safety.
**Architecture:** existing detector journal -> one selected policy's durable decision outbox -> one policy-neutral executor -> existing quote/exit logic; one wallet transaction authority; funding and financial accounting out of the time-critical path; read-only monitor.
**Stack:** existing Python 3.12, aiohttp, sqlite3, eth-account/eth-abi, Alchemy HTTP and WS, chain 4663. No paid services, additional wallets, frameworks, internal cost-based scheduling or new daemons proposed.
**Baseline:** Ld0g22/Blackswan b5e4a69aa83534bab34536fd5ed17afad8ffc4f0. Historical candidate Ld0g22/BlackswanNovember 5bd3c2b6914d85fc703a17190d5834a7f7cf8b45 (Build Two provenance). ## Global invariants and proposals requiring approval
- Detector decode, discovery universe, event schema, recovery semantics and verified historical implementation frozen for first pass. Internal CU enforcement is a separately gated change (operator previously requested removal); do not change detector as a side effect of selector work.
- Keep selection rule (concentration: first canonical trade timestamp inclusive, 30s exclusive end, largest transaction buy share <=25%, aggregate per transaction, same eligible universe and bans; buying blocks: existing policy and configured inclusive 3–10 range where selected). Do not change buying-block observation anchor inadvertently. Keep two independent selector-specific deployments, never simultaneously on same wallet.
- Keep requested stake, purchase count, sacrifice amount, enabled/disabled, block/seconds wait where supported, optional activity rule, explicit exit fractions and reserve, bans, spend caps including uncapped setting; no silently inserted limits. No new automatic sale or sacrifice liquidation rule. Preserve old campaign identity/config exactly when recovering legacy positions.
- Remove local trading-opportunity age gates in NEW clean campaigns; report lag as measurement, not a reason by itself to turn a mathematically valid selection into UNKNOWN. Do not reinterpret old historical/recovered decisions as newly authorised trades. Proposal: only live-observed admissions while explicitly armed, never buy a historical batch on restart; recover signed intents and existing positions. For an interrupted *unsigned* live entry or a genuine conflict/failure, record actual reason and end that entry instead of retrying indefinitely into a different price regime. A future freshly approved re-entry policy would be separate. A temporary read failure during ongoing observation can be recovered; decision records preserve original times and completeness. Explicit approval required for the no-age-gate and retry semantics; no substitute deadline.
- Observation boundary and survival block count are trading rules, not scheduling timeouts. Keep individual I/O timeouts, transport rate-limit handling, contract minOut, ordinary router expiry relative to fresh execution, single nonce owner, exact signed bytes and durable journal. Distinguish a not-sent signed intent from an uncertain broadcast. Never cancel reconciliation or release a nonce merely because a timer expired.
- Do not remove user-owned money protections just to reduce lines. Prioritise latched exits over new nonce acquisition; prepare independently. No concurrent live writers. No automatic fund movement except expressly authorised conversion policy. No automatic new deposits or allowances beyond existing scoped behavior.
- No automatic schema migration of old databases. Archive old code and keep an explicit recovery entrypoint on its pinned revision. Old campaign data read-only for comparisons. No deleting old branches, histories or positions.

## Target lifecycle and boundaries
Detector emits immutable launch, selector emits exactly one decision/revocation under existing interfaceVersion=1 (selectionId, tokenKey, event, venue, decisionAt; canonical evidence for concentration). Adapter validates identity and policy-neutral evidence envelope without interpreting selector name for execution. Proposed clean executor has a single processSelection(selectionId) lifecycle. With sacrifice: accepted -> sacrifice intent -> receipt -> waiting for target head -> survival proof -> main intent -> receipt -> position; without sacrifice, skip only those steps. State durably records actual submitted/confirmed transactions and genuine failures; a waiting state is not a failure. No repeated queue promotion. Wallet authority accepts a prepared transaction only after fresh status/cap/revocation checks, commits intent before signing submission, reconciles independently. Existing exits and receipt reconciliation continue when admissions close. Head and receipt notifications wake waiting work; bounded polling fallback is sufficient, no new scheduling framework. One active RPC reader per operation and bounded independent read concurrency; no per-pool unbounded threads or tasks. A WS swap is a hint/evidence subject to canonical confirmation, not proof of completeness; getLogs fills every gap, headers validate ancestry. Never accept partial concentration evidence as PASS. Record actual chain cutoff, observed cutoff head, last covered timestamp, decision, quote start/end, sign, send, receipt, target head reached and cause of delays. Use chain timestamps for chain semantics, monotonic clock for elapsed local durations. These are measurements, not admission deadlines.

## Main design choice
Prefer subtractive cleanup using proven quote/tracker and detector boundaries, not another wholesale rewrite or adding another supervisor. A straight rollback would also restore old delays and lose approved config/ban behavior; another patch would preserve branching and deadlines. New runtime code should be shorter because legacy mode machinery is isolated, not because essential transaction proof was removed. Proposed no-age-gate policy and automatic idle WETH conversion require user review; current code remains unchanged.
